# 查看器 UI 设计偏好

根据 2026-10-11 对旧 Agent 与当前 Codex 会话的查看器对话整理。精简摘录：`C:\Users\leaf\AppData\Local\Temp\viewer-ui-dialogue-excerpt.jsonl`。

## 明确表达过的偏好

### 1. 先让人看懂，再展示系统怎么实现

- 文案使用用户熟悉的词，避免把内部模块、文件写入过程或开发术语直接搬到页面上。
- 重要概念要直说，例如把难懂的画像层说明改成“全局记忆”“用户画像稳定层”“用户画像临时层”。
- 若一段说明删掉也不影响用户判断或操作，就不要让它常驻页面；确实需要时放进悬停提示或问号帮助。
- 不清楚按钮的作用、操作太难理解，说明交互或命名需要重做，不能只靠用户记住说明文字。

### 2. 页面要清爽，有明确层级，减少常驻说明

- 说明按用途安排位置：当前状态、失败原因、操作代价和必要步骤留在页面上；较少查看的解释放到 tooltip/help；成段的背景说明收进折叠区。
- 低频或占空间的管理功能不要默认塞在侧栏；适合时改为用户主动打开的 dialog。
- 相关内容应有清楚的分组。用户明确要求用边框表现两个操作区是并列关系；边框应帮助看出结构，不要为了装饰到处加框。
- 用户曾要求增加同组信息之间的留白。内容分组要松紧有序，不能挤成一团。

### 3. 操作控件要靠近它所作用的内容

- 不要让一个小按钮独占一行、与输入框或状态信息脱节；相关操作尽量与对应组件同一行。
- 一组同类操作保持并列，例如“预览结果”和“添加到临时层”、“场景报告”和“合并报告”。
- 全站刷新操作统一收束到顶栏，不要每页重复摆放不同位置的刷新按钮。
- 只保留有明确用途的动作。用户曾要求删除 L1 的“清空”，并质疑没有实际价值的“导出当前视图”。

### 4. 写入操作要直观、可预期

- 操作名称要让用户知道会发生什么；“定位”“确认”等含义不清时，应在交互本身解释清楚。
- 选择下拉选项只应更新待提交的值；实际写盘要有独立、清楚的确认按钮，并显示“当前值 → 将改为”的结果。
- 常用编辑入口与原始数据、正文纠错等高级操作分开；后者默认收起，避免编辑窗口初始就铺满字段和说明。
- 先给预览，再执行写入；预览应明确列出新增、保留、删除的数量和影响。
- 合并画像时的明确预期是：默认保留稳定层旧条目，只追加临时层中的新条目；整体替换必须是明确选择，不能让用户意外删掉全部旧内容。
- 破坏性或不可逆的后果需要在操作前可见，不能只藏在帮助提示里。

### 5. 阅读舒适度和一致性

- 全站字号统一略微增大；已接受的方向是整套字号令牌整体上调约 1px，同时保留层级差异。
- 标题层级必须稳定，不能因组件位置不同而退回浏览器默认字号、出现小标题比主标题还大的情况。
- 长文本不应撑高表格行。行高保持一致，正文使用单行省略，完整内容通过悬停查看。

### 6. 主题与语言

- 需要深色 / 浅色主题切换。
- 英文翻译要覆盖完整界面，包括工具提示、错误、空状态、确认流程和动态生成的文字；切换语言不能卡死页面。
- 主题和语言切换入口应统一、容易找到，并延续当前页面的偏好设置。

## 已被用户选定的运行体验

- 查看器源码更新后自动部署，已打开页面自动重载。用户已明确选择自动重载，并接受未提交输入可能丢失。
- 这是运行行为偏好，不应误解为可以静默丢弃当前页面中的写入表单；具体写入仍要给出清晰的预览和后果。

## 当前项目已有的视觉约定

以下是仓库已有的查看器设计契约，适合作为延续基线；它们不一定都是用户单独明确表达过的审美偏好：

- 界面外壳保持低彩度，颜色主要表达记忆温度或状态，不用强调色装饰普通按钮。
- 组件外观由 Vue 3 + Element Plus 保持一致，业务图形和数据形状由查看器自己的样式表达。
- 控件尺寸、字体令牌、滚动层级保持统一；避免同类控件在不同页面各自长相。
- tooltip/help 采用键盘可聚焦的实现，兼顾触屏和无鼠标操作。

具体样式契约仍以 [`../../../viewers/assets/viewer-theme.css`](../../../viewers/assets/viewer-theme.css) 为准。

## 后续设计检查表

1. 首屏是否能看出页面用途和最重要的信息？
2. 每段常驻说明是否会影响用户正确操作？不会的话，是否能缩到 tooltip/help 或删除？
3. 按钮是否和对应输入、状态或结果放在一起？是否存在孤零零占一行的次要按钮？
4. 相关区块是否有清楚的边界、留白和并列关系？
5. 写入前是否能看清将新增、保留和删除什么？默认行为是否保守且符合用户预期？
6. 长文字是否会破坏表格或面板的对齐？字体层级在弹层、侧栏和主内容区是否一致？
7. 深浅主题、英文、错误和空状态是否都完整可用？
8. 是否加入了没有实际用途的动作、解释或装饰？删掉一个元素后是否更清楚？

## 不应过度推断

目前没有足够证据把某种具体字体、品牌色、圆角大小或“卡片化程度”认定为用户偏好。后续应优先遵守上面的布局、可读性和文案原则，以及项目现有主题契约；遇到会明显改变整体视觉方向的选择，再结合实际页面和用户反馈决定。
