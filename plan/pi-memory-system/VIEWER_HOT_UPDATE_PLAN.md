# 查看器热更新 **（3/3 done）**

让正在运行的查看器在源码更新后自动部署新文件，并让已打开的页面及时应用新版本，不再依赖重启 Pi 会话或重新启动查看器。

## 背景与问题

- `index.ts` 的 `session_start` 只在扩展进程中部署一次；`scripts/l1-admin/viewer.mts` 也只在启动时部署一次。
- 写盘桥从 `{profile}/memoryDB/` 静态托管页面，响应已设置 `Cache-Control: no-store`；它不会监听仓库 `viewers/` 源码。
- 浏览器没有检查部署清单是否变化的逻辑，所以源文件变化后，部署目录和已打开页面都不会自动更新。

## 目标与验收

- 查看器启动后，源码 `viewers/` 有变化时，自动把变更同步到当前 profile，复用 `deployViewers` 的哈希比较、原子写入和文件归属保护。
- 已打开的页面能发现部署版本变化并应用新版，无需重启 Pi 扩展或手动重新运行部署。
- 浏览器语言和主题偏好继续保留；部署失败时继续提供当前版本并给出可见诊断。
- 不对扩展所有运行实例无差别增加后台轮询；热更新由专用查看器启动器提供。

## 范围

- `scripts/l1-admin/viewer.mts`：查看器运行期间监听源码变化并增量部署。
- `viewers/assets/viewer-core.js`：检查已部署清单变化并通知已打开页面更新。
- `viewers/assets/viewer-i18n.js`、`viewers/assets/viewer-theme.css`：更新提示文案和样式（如需要）。
- `README.md`、`scripts/l1-admin/README.md`：说明热更新行为及关闭方式（如需要）。

## 不做的事

- 不在生产 Pi 扩展进程中常驻监听文件系统；现有会话启动部署机制保持不变。
- 不引入 Vite、打包步骤或新的 npm 依赖。
- 不监听 profile 的记忆数据文件；只处理仓库 `viewers/` 前端源码。

## 方案设计

沿用现有唯一部署实现 `deployViewers(profilePath)`。专用启动器监听源码目录的嵌套变动，去抖后部署一次；多个文件连续保存时合并为一次部署。客户端定期读取已部署的 `viewer-manifest.json`，发现 `version` 改变后自动重新加载页面。同步失败时记录日志并保留已部署页面。

应用新版需要页面重新加载，因为页面脚本以普通静态资源加载、没有 HMR 运行时。用户选择自动重新加载；页面内未保存的输入可能随刷新丢失。
