# 修复会话关闭与在途流水线任务的生命周期竞态

让 worker 关闭流程与在途任务的真实结束协调，防止任务回调继续使用已关闭数据库，以及旧会话回调污染新会话状态。

## 目标

- 后台任务在运行时关闭会话，不出现数据库已关闭错误或未处理的 Promise 拒绝。
- 数据库句柄保持有效直到使用它的执行器及收尾回调结束。
- 重复关闭、关闭后立即重开以及 profile 切换均有明确行为。
- 旧任务只能更新其原 profile 的任务账目，不能清空新会话的忙碌状态、使用新会话上下文派发任务或关闭新连接。

## 现状依据与推荐方案

- `index.ts:622–630` 在 session_shutdown 调用各层 reset 和 worker reset。
- `memory/pipeline/worker.ts:246–250` 立即把 busy 设为 false 并关闭 jobs 数据库，但正在等待 `runJob()` 的 drain 没有被取消或等待。
- L1/L2/L3 执行器及早退出回调也持有数据库引用；只修 worker 最后的 `getJob()` 不能覆盖全部关闭后访问。
- drain 的 catch 还会通过同一个句柄调用 `complete()`，数据库关闭后可能在错误处理里再次抛错。
- 上述为静态证据；实施先用延迟结束的假执行器复现，核对宿主 session_shutdown 与新会话事件实际顺序。

推荐采用“停止新调度、保护在途句柄、结束后释放”的最小修复：

1. worker 跟踪在途执行 Promise、其 profile 与会话代次；reset 清除可用于派发的上下文，但不提前宣告在途执行已经结束。
2. 无任务时可立即关闭；有任务时延期关闭数据库，直到执行器及收尾处理结束。正常退出不新增强杀子代理行为，也不等待完整 LLM 任务才让用户关闭会话。
3. 会话重新启用时恢复轮询/调度；旧任务结束后仅释放自己持有的资源。相同 profile 已恢复使用的连接不能被旧 reset 延迟关闭。
4. 旧代次结果仍可完成原任务账目；面向会话的通知、后续调度和状态重置必须验证代次。对关闭期间完成的 L1 后续编排，将待续任务写入原 profile 的 queued 队列，在该 profile 的有效会话恢复后才派发，避免丢掉积压排空链。
5. 数据库操作的失败处理与调度入口的 Promise 拒绝都有兜底；错误处理不再次依赖已经失效的句柄。
6. 核对三层等待循环、早退出回调和状态栏心跳；如需取消 UI 更新，用同一生命周期约束保护，保留持久化完成信号。

## 流程

### 主路径

1. 活跃会话给 worker 提供上下文；worker认领任务并记录对应的 profile、会话代次与执行 Promise。
2. 会话关闭时暂停新派发并清除会话上下文；无在途任务就关闭连接，有在途任务就保留其所需连接。
3. 任务完成、失败或进程早退后，按原 profile 处理任务账目，并安全结束执行器、回调与心跳。
4. 若该 profile 仍暂停且无人使用连接，关闭连接；若会话已恢复，不关闭它正在使用的连接。
5. 新会话恢复调度，待续的 L1 编排由当前有效上下文接续；旧回调不能修改新会话控制状态。

### 意外与边界

| 场景 | 处理 |
|------|------|
| 空闲时关闭、重复 reset | 立即或幂等释放，不创建新连接或重复回调 |
| 任务等待期间关闭 | 暂停新派发，保护在途句柄，任务按既有完成/超时机制结束 |
| 子进程异常退出恰逢关闭 | 早退出处理能访问有效原连接，最终状态只记录一次 |
| 关闭后立即重开同一 profile | 旧任务仍计为在途；旧清理不能关闭当前连接或把新任务 busy 清掉 |
| 切换到另一个 profile | 原任务与资源仍归原 profile；新上下文不用于原任务的后续编排 |
| 执行器拒绝或数据库收尾失败 | 记录原始错误；兜底失败也被处理，不产生第二次未处理拒绝 |
| 旧轮询/微任务在关闭后触发 | 看到暂停或代次不符即退出，不使用旧上下文派发 |
| 关闭期间 L1 完成且仍有积压 | 保留待续编排；该 profile 恢复会话后继续，不能静默丢掉下一批 |
| 宿主进程被强杀 | 继续依赖现有运行记录、run lock 与重启恢复机制，本计划不重做崩溃恢复 |

## 风险

- session_shutdown 可能对应进程退出、会话切换或扩展重载，实施第一步核对宿主实际契约后回填证据；延期关闭不能变成阻塞用户关闭。
- 全局数据库实例缓存存在多个消费者；延期释放必须识别具体句柄与使用者，不能仅按 profile 字符串关闭。
- 会话代次保护要同时覆盖 finally 与通知回调；仅对正常成功分支检查代次仍会残留竞态。
- 本计划与原子认领计划共用 worker 和 jobs-db；执行时先完成原子认领，再处理生命周期，最后组合验证。
