# 修复流水线跨进程认领与入队竞态

把同一 profile 的队列单飞和入队去重落实到 SQLite 原子操作，避免两个 Pi 进程同时派发不同后台任务。

## 目标

- 同一 profile 的 L1/L2/L3 队列最多有一条 running 任务。
- 两个进程同时入队同一层时，只产生一条 queued/running 任务。
- 保持现有 L3 末位优先、跳过熔断层、L1 积压排空后再排 L2 的调度规则。
- 用真实独立进程复现并验证竞争；顺序调用断言不能替代该验证。

## 现状依据与方案

- `memory/pipeline/worker.ts:150–158` 的 `hasAnyRunning()` 与 `claim()` 分属两个数据库操作。
- 可发生的交错：A、B 都查到没有 running；A 认领第一条；B 随后读取队列，挑到第二条并认领。`claim()` 只验证目标行仍 queued，因此两条都能进入 running。
- `memory/pipeline/jobs-db.ts:104–112` 的入队同样是先 SELECT 再 INSERT，存在跨进程重复入队窗口。
- `completeRunning(type)` 按层更新所有 running 行；若历史异常已出现多条同层 running，一次提交可能将它们一并标 done。
- 上述为静态代码证据；实施第一步补确定性复现，不把上一轮检查通过当作竞态已验证。

推荐方案：

1. 在 `claim()` 的同一条 UPDATE 中加入“全库不存在 running”的条件，例如 `AND NOT EXISTS (SELECT 1 FROM jobs WHERE status = 'running')`。影响行数为 0 表示没有认领权，worker 等下一次调度即可。
2. 将入队的查重与插入置于 `BEGIN IMMEDIATE` 事务内；重复时返回已有任务 ID，任何异常先回滚再交由现有日志路径处理。
3. worker 的前置空闲检查仅作为快速退出，不再承担互斥正确性；最终以数据库认领结果为准。
4. 完成信号遇到历史多条同层 running 时报告明确异常，避免一次提交批量标记完成；不自动选择、删除或修复历史任务。实现时核对 commit 调用者对异常的现有处理，保持返回契约可用。

## 流程

### 主路径

1. 触发器请求入队；数据库在写事务内返回已有活动任务，或插入新 queued 任务。
2. worker 按现有优先级读取可运行候选，跳过熔断或持有的层。
3. 数据库原子认领：目标仍 queued 且没有任何 running 时才更新。
4. 只有认领成功的进程启动子代理；竞争失败的进程保持队列不变。
5. 子代理提交后结束当前任务；worker 按既有规则安排下一批。

### 意外与边界

| 场景 | 处理 |
|------|------|
| 两个进程同时认领同一任务或不同任务 | 最多一次认领成功；失败方不派发子代理 |
| 两个进程同时入队同一层 | 返回同一活动任务 ID，只有一次 INSERT |
| 已有任意层 running | 其他 queued 任务不进入 running |
| 数据库忙、事务内抛错 | 回滚并记录错误，不残留打开的写事务；后续调度仍可工作 |
| 候选在认领前已被其他进程处理 | 返回未认领，不误改 finished_at、error 等状态 |
| 队首层熔断或 L3 比 L1/L2 更早入队 | 继续沿用现有跳过和优先级规则 |
| 存量数据库有重复 queued 或多条 running | 不自动清理；认领继续保守拒绝，完成操作不批量误标；异常写日志供人工检查 |

## 不做的事

- 不修复或启用旧 sub-memory 写入通道。

- 不调整提取模型、触发频率、超时参数或记忆内容。

## 风险

- WAL 与 busy_timeout 不能替代业务原子性；验证必须覆盖真实双连接/双进程交错。
- 新实现与旧版 Pi 扩展进程混跑时，旧进程仍可能走旧认领逻辑；修复生效后应重启使用该 profile 的所有 Pi 进程。
- `completeRunning` 异常处理必须核对各层 commit 的错误边界，避免数据已提交但收尾静默失败。
