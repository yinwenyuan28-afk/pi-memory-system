# 查看器跟版重写（源码进仓库 + 激活时同步）

把 `{profile}/memoryDB/viewers/` 里那份手维护的 L1 records 查看器重做，并**补上让它不再落后于 schema 的机制**：
源码进仓库、扩展激活时按内容哈希原子同步到运行位置，L2/L3 各加一页，写回只加任务状态切换。

## 背景与问题（2026-10-08 实测）

`records-viewer.html` 停在 **2026-09-14**，此后后端每次改动都把它甩开：场景池（09-15）、L2 归档（09-27）、
type 收束与项目归属（10-02）、管线（10-04）、`taskState`（10-08）。

根因不是"忘了更新"，而是**没有任何东西负责让它跟版**：它不在 git（`git ls-files | grep .html` 为空）、
`package.json` 不发布前端资源、`memory/paths.ts:220` 的 `VIEWER_DIR` 全仓库无人引用、
扩展也不生成它（全仓库没有一处把 HTML 写进 profile）。

具体缺口（逐条实测）：

| # | 缺口 | 证据 |
|---|---|---|
| 1 | `taskState` 零支持 | viewer 全文搜不到 `taskState`；当时 18 条记录已带 `done`/`dropped` |
| 2 | 用 `scene_name`（官方声明"只是历史快照"）而非 `scene_id` → `scenes.json` | `paths.ts:59`、`scene-pool.ts:4` |
| 3 | 无项目维度 | `metadata.project` 419 条、`scope` 672 条 |
| 4 | `value-check-log.jsonl`（118 条被丢弃记录 + 理由）零视图 | 只看 records = 纯幸存者偏差 |
| 5 | 注释自称"与 quality.ts 1:1"，但 `prune/judgePrune/protectedPriority/percentile` 出现 **0 次** | `quality.ts` 已把"热度"与"删除资格"拆开 |
| 6 | L2 全域零视图 | 15 个 live 块 + 1 归档 + ledger + 两份 members 侧车 |
| 7 | L3 零视图 | 游标 + `MEMORY.md`/`USER.md`/`USER-temp.md` 的条目与预算 |
| 8 | 自动加载只扫 60 天 | 实际 24 个分片、跨度更久 |
| 9 | 无版本标记 | 打开的人无法判断手里是哪天的 |
| 10 | `vue-viewer/`（08-23）已被取代 | 无 node_modules/dist，`quality.js` 只有日历天衰减 |

## 目标

1. 查看器源码进仓库，扩展激活时**自动同步**到 `{MEMORY_DB}/viewers/` —— schema 变更不再落后。
2. L1 页重写：补齐 `taskState`、场景/项目维度、value-check 留痕、真实质量分与淘汰候选。
3. 新增 L2 场景页、L3 画像页、总览页。
4. 界面上可把 `work_task` 标成 `done`/`dropped`/`open`。
5. 质量分与源码一致性由**回归门禁**保证，不再靠注释声明。

## 已确认决策

| 决策 | 理由 | 被否选项 |
|---|---|---|
| 源码进仓库 + 激活时原子同步 + 版本清单 | 治本；`PLUGIN_ROOT` 已有仓库根，`profile.ts` 已有 tmp+rename 原子写先例 | 只留副本+自检（仍需人工复制）；只改内容（治标） |
| 写回只加 `taskState` 切换 | 与新功能天然配对；`applyTaskStateChanges` 已含写锁+审计+幂等，`--experimental-strip-types` 下 `.mts` 可直接 import（`migrate-task-state.mts` 是先例），**无需重构** | 再加恢复墓碑/场景改派（动 `scenes.json`，需对齐 `l1_commit` 写锁口径） |
| 共享资源用 **classic script**（非 ES module） | `<script src>`/`<link>` 在 `file://` 下可用，ES module 与 `fetch` 不可用 —— 保住「手动选 JSONL」的离线回退路径 | ES module（`file://` 全废） |
| 质量分 JS 是唯一 JS 副本，靠 parity 门禁守住 | 与仓库 `verify-*` 惯例一致，离线可用，不引入构建步骤 | 从 TS 生成 JS（需 bundler）；桥算分（离线不可用） |
| 多页 + 共享 assets | 单文件 SPA 更大更难维护 | 单文件多标签 |
| 阈值/版本/活跃日一律经 `.mts` 转发，不在 `.mjs` 里重写 | 这几项必须与源码同一份实现（否则"明明已部署却一直报漂移"这类 bug 会出现） | 桥里自己算一份 |

## 数据模型与契约

**仓库侧**（进 git，加入 `package.json` 的 `files`）：

```
viewers/
├── index.html            总览（数据健康 + 版本/漂移 + 三页入口）
├── records-viewer.html   L1
├── l2-viewer.html        L2
├── l3-viewer.html        L3
└── assets/
    ├── viewer.css        共享样式
    ├── viewer-core.js    共享工具（V：加载器/格式化/导航/版本/桥调用）
    ├── quality-core.js   质量分 + judgePrune + P75（唯一 JS 副本，由 parity 门禁守住）
    ├── records-view.js / l2-view.js / l3-view.js / index-view.js
```

**部署产物**（`{MEMORY_DB}/viewers/`）：逐文件 sha256 比对，只在变化时原子重写；
`viewer-manifest.json` 记 `{version, generatedAt, sourceRoot, files[], retired[]}`，
`version = 包版本 + 内容哈希前 8 位`。`vue-viewer/` 一次性移入 `backups/viewers-retired/`（**不删除**）。

**桥端点**（`scripts/l1-admin/viewer-bridge.mjs`）：`POST /api/tombstone`、`POST /api/task-state`、
`GET /api/l1/shards`、`GET /api/l1/active-days`、`GET /api/l2/blocks`、`GET /api/limits`、
`GET /api/l3/backups`、`GET /api/profile-files`、`GET /api/health`、`GET /api/viewer-status`。

**taskState 写回语义**：复用 `applyTaskStateChanges` —— 写锁内就地改写；只接受存活 `work_task`；
幂等；审计写 `metadata.taskStateChange`（`by:"user"`）；单批 ≤50。

## 流程

### 主路径
1. `node scripts/l1-admin/viewer-bridge.mjs` → 打开终端打印的 `http://localhost:5174/viewers/index.html?port=5174`。
2. 页面自动 fetch 各层数据（或走桥的列目录端点拿全量分片）。
3. 页面右上角显示已部署版本；源码改过但未部署时标黄「源码已更新未部署」。
4. L1 页对 `work_task` 卡片给 `[待办]/[已完成]/[已废弃]` 切换 → `POST /api/task-state` → 就地改写 → 显示审计时间。

### 意外与边界

| 场景 | 处理 |
|---|---|
| `file://` 直接打开 | 自动加载与写回不可用 → 顶部显示明确提示与桥命令；手动选 JSONL 仍可用 |
| 缺 `viewer-manifest.json` | 静默不渲染版本 chip |
| 无写盘桥 | 活跃日退回 `hit-stats.json` 侧车（并标注"可能滞后"）；L2 无法核对索引↔磁盘；L3 画像文件读不到（显式告警）；无法列全部分片（退化为最近 90 天） |
| `l0/conversations` 不存在 | `/api/l1/active-days` 返回 `available:false` → 页面退化为日历天并如实标注 |
| `scene_id` 不在池中 | 显示原始 `scene_name` + 「未归类」标记与 tooltip，不把它当 canonical |
| 记录 `deleted:true` 且 `taskState:"done"` | 两根轴分别渲染，不合并语义 |
| 部署时目标文件被占用（Windows） | tmp+rename 重试（沿用 `profile.ts` 的 `[0,50,50]ms` 退避）；失败只记日志，不阻塞激活 |
| `viewers/` 下有清单之外的文件 | 不碰；只有 manifest 记录归属的才重写/退役 |
| 写锁被占（后台 L1 在跑） | 端点返回 `lockError`，界面提示稍后重试，**一条都不写** |

### 过程中发现并修掉的真实缺陷（都不是推断，是可复现的）
1. **桥不解码 URL** → 浏览器的 fetch 把中文文件名百分号编码，L2 的块（全是中文名）整批 404，
   页面不报错只是显示索引兜底值。修：`decodeURIComponent` + 两个回退候选。
2. **画像文件读不到** → 桥只挂载 `memoryDB`，而 `MEMORY.md`/`USER.md`/`USER-temp.md` 在 profile 根；
   页面里 `../../USER.md` 必然 404。修：新增 `/api/profile-files` 白名单端点。
3. **活跃日时钟滞后** → 侧车 `activeDays` 只在命中库被打开时刷新，实测 29 vs 实际 30 天，
   导致 3 条记录从「冷」错标为「待观察」、整个直方图偏一格。修：新增 `/api/l1/active-days` 读 `l0/conversations` 真源。
4. **桥解析 CLI stdout 会误报失败** → `autoBackup` 会先打一行日志，整段 `JSON.parse` 把成功报成 500。修：`parseCliJson` 从第一个 `{` 起解析。
5. **卡片漏了记录 id** → id 是 `l1_fix`/`l1_task_state` 的操作句柄（旧版有），重写时漏掉，补回。
6. **`USER.md` 是 1921/2200 而非超限** → 计划初稿按 `ls` 的字节数（4745）误判为"超 2200"；用真实解析器核对后更正，
   页面也据此标注"预算不是字节数"。
7. **`node --check <file.mts>` 对含 import 的 `.mts` 假绿**（后续加「CLI 脚本语法」门禁时发现）：
   Node 24 实测，`.mts` 带 import 时 `--check` 静默返回 0，而同样内容写成 `.mjs` 才会报错 ——
   这个组合恰好对全部真实 CLI（都以 import 开头）失效。**一条从不报警的门禁比没有门禁更糟**，
   故 ⑮ 改成 `module.stripTypeScriptTypes` 去类型后从 stdin 交给 `node --input-type=module --check -`，
   并对 `.mts`/`.mjs` 两类文件分别验证过会变红。

## 追加（同日）：界面打磨

功能补齐后单独做了一轮视觉重做，触发点是用户指出的"现在还存在很多原生的滚动条"。做法是**先量化、再改样式**，
因为这一轮的验收无法靠肉眼看截图（见文末「验收方式的局限」）。

### 实测到的起点问题

| 指标 | 改前 | 改后 |
|---|---|---|
| L1 页可见滚动容器 | **54**（其中 53 个是卡片正文 190px 内部滚动） | **1**（只剩侧栏） |
| 侧栏滚动条宽度 | 15px（浅色经典，带箭头） | 11px（暗色细条） |
| 页面滚动条宽度 | 15px | 10px |
| 全页字体级数 | **9**（12.16 / 12.48 / 13.12 / 13.76px … 相邻差 0.3px） | **4**（21 / 13 / 12 / 11px） |
| 状态药丸数量 | 7230 个 `.chip`（12 个/卡） | 3104 个 `.chip` + 4126 个 `.metric` |
| 标签页选中态 | 无样式（`switchTab` 切了 class 但 CSS 没对应规则） | 有（底色 + 墨色下划线） |
| `--accent` = `「冷」` 色 | 同一个 `#4a9eff`，按钮与"已冷却"撞色 | 外壳改为无彩度墨色，色相全留给数据 |
| `.entry .idx` 对比度 | 3.14:1（11px 文字，不达标） | 5.9:1 |

### 写进 `viewer.css` 文件头的四条契约

1. **色相属于数据，不属于装饰**：外壳（导航/按钮/链接/边框/统计）一律无彩度；六个「记忆温度」是全页仅有的成组彩色。
2. **形状编码种类**：实心彩色药丸 = 已确定状态；虚线 = 未落定（open / 未归类）；点线 = 已搁置（dropped）；
   无色方块 = 分类值；等宽 token = 度量值。度量值用 `.metric`，不再混进药丸。
3. **一层只有一条滚动轴**：页面 / 侧栏 / 表格与 JSON 三处，卡片正文只做截断预览（完整正文在弹层）。
4. **数字等宽 + tabular-nums，字号只走六级令牌**。

### 过程中发现并修掉的问题（都是"静默失真"，浏览器不报错）

1. **写 `scrollbar-color` 反而让滚动条变宽**：实测不指定 = 11px，指定 = 16px 且带箭头（比不指定更糟）。
   真正让原生控件变暗的是 `:root { color-scheme: dark }`；标准属性只在 `@supports not selector(::-webkit-scrollbar)`
   里给 Firefox 兜底，Chromium 走 `::-webkit-scrollbar`。
2. **CSS 特异度把温度色吞了**：兜底色 `.bar-track > i`（0,1,1）压过工具类 `.c-hot`（0,1,0），
   六个条形图与 567 张卡的温度条**全部渲染成兜底灰**。改成 `:where(.bar-track) > i` 让出特异度。
   这正是 frontend-design 提醒的那类"类选择器互相抵消"。
3. **对比度的第一版算法是错的**：`getComputedStyle` 对 `color-mix` 结果会原样返回 `oklab(...)`，
   把它的三个数字当 RGB 用会算出 6~11 的假高值。改为 canvas 画 1px 再读回 sRGB 字节，才发现
   状态下药丸叠 14% 同色调淡底会把红/品红压到 3.9~4.4 → 最终放弃淡底，只留同色描边（全色相 ≥ 4.7:1）。
4. **同色淡底这条路走不通**：淡底混进 `--panel2` 会掉对比度（4.16~4.44，不达标）；混进更暗的基色虽然能过，
   但药丸与卡片底色只差 1~2 级、形状糊掉。所以"颜色只走文字 + 描边"是权衡后的结论，不是随手选的。
5. **`.del` 被当成"错误"复用**：`已归档 / 文件读不到 / N 项异常 / 索引缺块` 都用 `.chip del`（"记录不成立"的红）。
   新增 `.chip.err` 承载读失败与异常；"淘汰候选"改琥珀 `.chip.prune`（候选 ≠ 事实）。
6. **直方图"温度计"渐变放弃**：渐变的 `background-size` 只能写死像素，而柱子可用高度取决于 val/lbl 行高，
   写死必然对不上，且无法用百分比表达"整列高度"。改为单色相 `--cold`，温度由旁边的标签条形图承担。
7. **`overscroll-behavior: contain` 会把滚轮吃掉（用户报"L2 页鼠标滚动失效"）**：本轮把它当作"防止滚动传染"
   的优化加在了 `aside` 与 `.wrap-scroll` 上。实测（对照实验，同样坐标同样滚轮位移）：
   光标落在块表格那个 `overflow:auto` 但**内容并不溢出**的包装层上时，页面 `scrollTop` 纹丝不动；
   把 `overscroll-behavior` 强制改回 `auto` 后，同一个手势立刻把页面滚了下去。
   即**只要容器带 `contain`，滚轮就被它吞掉，哪怕它根本没有可滚内容**；而 L2 的块表格占了内容列大半，
   侧栏在内容不长时也不溢出 → 两处都成了滚轮死区。修法：`aside` / `.wrap-scroll` 一律回到默认的滚动链接，
   `contain` 只保留在弹层（打开弹层时把滚轮拦住、别滚动背景，这才是它该用的地方）。
   这个坑当初不该顺手加 —— 原版 CSS 里本来就没有 `overscroll-behavior`。

8. **`?port=` 被静默丢掉（用户问"为什么一定要用桥打开、直接打开就显示无写盘桥"）**：两条路径都在我们自己可控的代码里。
   ① `viewer-core.js` 的**顶部导航链接不带 `location.search`** —— 从带 `?port=` 的总览页点一下导航就变只读，
   L2 立刻冒出 3 处"无写盘桥"（同一页里侧栏按钮却带了 query，属漏改）；
   ② 桥的根路径 `/` **就地返回 `index.html`**，其相对引用的 `assets/*` 在 `/` 下解析成 `/assets/*`，
   而那不在托管范围内 → CSS/JS 全 404、连 `window.V` 都没有；偏偏桥启动打印的第一行就是这个根路径（终端里可点）。
   修：导航带 query、根路径 302 到带 `?port=` 的总览页、缺 query 时给可操作提示（与 `file://` 提示分属两个分支）。
   诊断靠的是"**这句文案只在 http 下出现**"这条线索做二分，而不是猜浏览器行为。

### 门禁 98 → 130 项（新增 ⑯ 设计契约节与 ⑰ 打开方式契约节）

断言：JS 无硬编码色值（配色单源）、`scrollbar-color`/`scrollbar-width` 只出现在兼容兜底块内、
`overscroll-behavior` 不落在 `aside`/`.wrap-scroll` 上且仍留在弹层上、
`.c-*` 六个温度工具类仍在且不被兜底色压过、六级字号令牌与 `color-scheme: dark` 在场、
页面脚本不再使用 `card-scroll` 且 `.card-body` 声明了 `-webkit-line-clamp`。
⑰ 节断言：顶部导航链接携带 `location.search`、桥的根路径 302 且带上 `?port=`、缺 `?port=` 时有可操作提示、
且该提示与 `file://` 提示分属不同分支。

三条位测试教训（都真的注进去验证会变红）：
- "只出现在兜底块内"第一版写成只看兜底块**之前**，对写在块**之后**的声明无效 —— 注入验证时未变红，改成区间判定后才咬人。
- 十六进制色值 / 改回 `.bar-track > i` / 在块后加 `scrollbar-color`：逐条变红。
- `overscroll-behavior` 分别注入 `aside` 与 `.wrap-scroll`：各自变红并指名道姓。

### 验收方式的局限（必须记着）

当前会话模型不支持图像输入，派出去的子代理同样看不到图，**所以四页的原始截图我无法判读**。
替代证据全部是可量化的：滚动容器数与滚动条实际宽度、字号集合、每对文字/底色的对比度（canvas 像素回读）、
元素几何与网格列数、温度工具类的实际计算色（确认 567 张卡是 305 watch / 153 warm / 64 cold / 23 hot / 22 new 而非一片灰）、
以及四页渲染后的文本内容（确认无"加载中/尚未加载"残留、无 JS 异常导致的空段）。
**结论：契约与可读性下限有数字保证；"好不好看"仍需人看一眼。**
