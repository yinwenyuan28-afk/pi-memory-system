# L1 任务生命周期标记（已完成 / 已废弃）

给 `work_task` 补上「任务是否还开着」这一维状态，并提供 agent 与用户两侧的标记入口；状态存为**顶层闭集字段**，不复用 `deleted`。

## 背景与问题（2026-10-08 实测）

- `work_task` 是四种类型里唯一有生命周期的（提取定义即「有后续动作/deadline 的待办」），但存储上当一次性事实处理。
- 真实库 `profiles/default/memoryDB/l1/records`：24 分片、983 行、840 个 id、LWW 存活 567 条，其中 **37 条存活 work_task**（2026-08 起 5 条、2026-09 起 32 条）。37 条**全部**带 `metadata.status`，取值 7 种：`todo` 25 / `done` 4 / `deferred` 3 / `confirmed` 2 / `doing` 1 / `blocked` 1 / `decided` 1。词表是提取器自由文本，`confirmed` / `decided` 并不是任务状态。
- **这个字段没有任何读取者**：召回候选投影 `L1RecordCandidate`（`memory/search/hybrid-recall.ts:40-48`）只取 content/type/priority/scene_name/createdAt；自动注入只渲染 `- ${content}`（`index.ts:856-859`）；L2 精简投影显式剔除 metadata（`memory/l2/read-tool.ts:32-43`）；quality/prune 不看。仓库里唯一的"读"是 `scripts/verify-project-scope.ts:194,200` 的夹具断言（验证既有 metadata 键被保留），不是业务读取者。⇒ 写了没人读，等于死字段。
- 唯一能让任务状态改变的路径是 dedup（`memory/l1/prompts/dedup.md:117`：`work_task：状态变化 → 倾向 update`），而它要求该任务**再次出现在新消息里**。任务做完后再没被提起 → 记录永远停在 `todo`，且召回是纯相似度，7 周前的 todo 照常注入。库内实证：正文写着「已执行」而 `status` 停在 `todo` 的 2 条（`l1_1789097476492_w43k`、`l1_1789836500009_r9i9`）、2026-08 起「待用户决策」至今仍 `todo` 的 4 条。
- **不存在自动淘汰**（比"兜不住"更准确）：`judgePrune`（`memory/l1/quality.ts:171`）的唯一调用点是同文件 `:279` 的 `getQualityStats()`，而它只喂 `/my-memory:l1:stats` 的展示（`index.ts:1641-1660`）。没有任何代码按淘汰判定删记录，且 `:184` 对 `effective > 0` 的记录直接返回 `eligible:false` —— 越被召回越不可能出现在候选里。
- 唯一注销通道 `deleted: true` 的语义是「记录不成立/被取代」，其三条入口（`l1_fix`、`/my-memory:l1:fix`、`l1-admin/tombstone.mjs`）都带纠错护栏（`memory/l1/fix-tool.ts:97-119`：证据 ≥20 字符、24h 防抖、高价值保护），不适合承载例行生命周期动作。

## 目标

- 任务状态可被 agent 与用户**低成本**标记：一次调用 / 一条命令，无证据门槛。
- 标记结果在**所有消费侧可见**：召回候选、自动注入、L2 场景整理。这是本计划的核心——只加字段不加读者，就是重演 `metadata.status` 的死字段。
- 标记**不毁数据**：保留记录 id、正文与向量，保留"这件事做完过"的知识，且可回退（reopen）。

## 已确认决策

| 决策 | 理由 | 被否选项 |
|---|---|---|
| 新增顶层字段 `taskState`，闭集 `open` / `done` / `dropped`，缺省即 `open` | 「记忆是否成立」与「任务是否关闭」是两根轴：前者是 `deleted`，后者是本字段。分开后数据能区分"被新版本取代"与"任务做完了" | 完成/废弃也写 `deleted: true` |
| 标记采用**就地改写**（id / content / 向量全不动） | 不烧 embedding、不重置 hit-stats、不产生 L2 成员死引用与孤儿 stats；`deleted` 的就地标记已是同款先例 | 走 dedup update 语义（旧 id 墓碑 + 新 id version+1） |
| 审计写独立键 `metadata.taskStateChange`，**不复用** `metadata.l1Cleanup` | `l1Cleanup.appliedAt` 是 `l1_fix` 的 24h 防抖数据源（`fix-tool.ts:109-115`）；复用会让刚关闭的任务 24h 内不可修正 | 复用 l1Cleanup |
| 已关闭任务**默认继续注入，但带中文状态标签**；另给 `recall.hideClosedTasks`（默认 false）开关 | "已经做过 X"本身常是某些问题的答案；彻底静音的需求由开关满足，且不毁数据、可逆 | 关闭即从召回剔除 |
| 只有 `work_task` 承载 `taskState`；`blocked` / `deferred` 归 `open` | 生命周期只需要"开/关"一根轴，细节留在正文；避免再造一套自由词表 | 把 `metadata.status` 的 7 个值升格为枚举 |
| agent 侧用**独立工具** `l1_task_state`，用户侧用 `/my-memory:l1:task`（含 list） | 与「一次操作一个工具」的既有分工一致（commit 写、fix 纠错、recall 读）；不复用 `l1_fix` 是因为它的三道纠错闸会把例行动作挡在门外，而不复用 `l1_commit` 是因为它是"写新记忆"语义、`records` 必填且要过 LLM 价值校验 | 扩 `l1_fix` 第三 action / 给 `l1_commit` 加 `stateChanges` 参数 |
| **不做**"只读侧解释 `metadata.status`"的过渡方案 | 成本近零但站不住：7 值自由词表映射不全（`confirmed`/`decided` 无法归位）；`status` 只有 AI 提取"顺手"写过，主代理直写路径（`prompts/injection/l1-contract.md` 的字段清单）根本没有这个键；无法表达 `dropped`，也无法被工具/命令**写回**纠正 | 先按 `status==="done"` 加标签、字段以后再说 |

> 关于"顶层 vs metadata"的取舍（供将来复评）：`rewrite.mjs` 的 `metadata: {...oldObj.metadata, ...}` 是展开合并，放在 metadata 里反而能绕开白名单问题；但 L2 精简投影**显式剔除 metadata**，放 metadata 等于 L2 永远做不到"只列 open"，语义分层也错（metadata 是模型自由扩展区）。故取顶层，代价是 `rewrite.mjs` 需补一行。

## 数据模型与契约

记录新增顶层字段（与 `deleted` / `version` 同级）：

```json
{"id":"l1_1789097476492_xtah","content":"…","type":"work_task","taskState":"open",
 "metadata":{"taskStateChange":{"from":"done","to":"open","at":"ISO","by":"agent","reason":"…"}}}
```

- 取值：`open`（待办/跟进中）/ `done`（已完成）/ `dropped`（已废弃、不做）。
- 缺字段 = `open`（存量记录无需迁移即语义正确）。
- `taskState === "done"` 与 `deleted === true` 无关；后者仍表示记录不成立。已 `deleted` 的 id 不接受状态标记（报错）。
- 标记写入：就地改写**最后一条活跃行**（LWW 口径，与 `commit-tool.ts:620-646,667-672` 一致；`l1-admin/tombstone.mjs:31-35` 标记同 id 全部活跃行是另一套口径，实测生产库当前"同 id 多活跃行"为 0 条，本计划取 LWW 最后一行并写进注释）→ `taskState` + `updatedAt` + `metadata.taskStateChange`；**不改** `content` / `id` / `version` / `metadata.status`（沿用 `deleted` 标记不 bump version 的先例；`version` 无任何真实读者，`l2/read-tool.ts:84-85` 的注释提到它但实现里没有 version 判定）。
- **定位原语写死**：`readdirSync(recordsDir)` 全部 `.jsonl` + 逐行 LWW 取最后一行（先例 `fix-tool.ts:24-39`、`commit-tool.ts:620-646`、`l1-admin/lib.mjs:42-65`）。**不得**复用 `loadL1RecordById`：它默认只看最近 30 天，且分片名用 `toISOString()` 的 **UTC** 日期枚举（`record-loader.ts:43-88`），而写入侧用的是**本地**日期分片（`commit-tool.ts:50-55,683`）——UTC+8 机器的 00:00–08:00 之间读不到当天分片，30 天窗口也会漏掉 8 月的存量。该不一致是既有缺陷，本计划的新工具不继承。
- 幂等：目标已是该状态 → 无操作并如实回报；id 不存在或已 `deleted` → 报错列出该 id，不静默跳过。

### 写入路径的字段继承（审查发现的静默丢失点）

除 `l1-admin/rewrite.mjs` 外，**dedup 的 update / merge 也是"新 id + 旧行墓碑"**（`commit-tool.ts:658-680` 的新行完全来自子代理本次输出），而 `dedup.md:117` 恰恰把"任务状态变化"指向 update。⇒ 一条被标 `done` 的任务日后被再次提及并判为 update 时，新版本会**静默回到 open**。三条措施：

1. `rewrite.mjs`（`scripts/l1-admin/rewrite.mjs:44-60` 是白名单重建）补 `taskState: oldObj.taskState`；
2. 提示词契约：`dedup.md` 的 code 段 + `agents/l1-extractor.md` 第六步模板注明"替换/合并一条 `taskState !== open` 的记录时，新记录必须继承该状态"；
3. 观测：`l1_commit` 返回体加软闸计数 `taskStateDroppedOnReplace`（本批有墓碑行、其原记录 `taskState !== open`，且本批没有新的 `work_task` 行携带 `taskState` 时 +1），让子代理在摘要里如实报告——与既有 `priorityDefaulted/provenanceMissing/overRecallBudget` 同格。

**不做**代码侧硬继承：batch 内"墓碑行 ↔ 替代行"没有结构化的对应关系（`metadata.replaced` 目前无任何写入方，`value-check.ts:335` 的注释指向一个不写它的地方），为此新增 linkage 字段属于更大的契约变更。

### 校验位置（`l1_commit`）

`taskState` 的闭集校验放在**确定性闸门块**（`commit-tool.ts:380-417`），与 `type` 同格：

- 非闭集值 → 硬闸拒绝整批（同 `type` 的 `:389-394`、`priority` 的 `:402-407`）；
- `deleted === true` 的标记行照 `:384` 豁免；
- 非 `work_task` 类型带该字段 → 忽略并计入 `taskStateIgnored`（放在 `:409-417` 的软闸循环，与 `provenanceMissing` 同格）；
- **不能**放到价值校验（`:430-527`）之后：那一段只在 `!isMainAgent && enabled` 时运行，放到其后等于 main-agent 路径完全绕过闭集校验；也不能放到写锁之后（"拿了锁再拒"）。
- 已核实价值校验不会丢字段：`value-check.ts:296-307` 的 `retype` 是 `{...rec, type}` 浅拷贝、`applyVerdictsToBatch` 只增删不改字段、`drop` 的记录不落盘。

### 注入格式（读取侧的对外契约）

自动注入块与 `recall_l1_records` 返回体携带 `taskState`；注入行统一带上 id（让自纠/关闭无需二次召回即可执行）：

```
- [待办] (l1_1789097476492_xtah) 需要为每条记录添加「和导师聊天」按钮…
- [已完成] (l1_1789097476492_2dfl) 毕业生切换现状…
- (l1_1789097476492_yia3) 前端 master_jyw 迁移状态…
```

- 状态标签只出现在 `work_task` 上；`(id)` 位置固定在行首标签之后。
- 拼装时把 content 内的换行折成空格（一行一条）。当前是原样拼接（`index.ts:856-859`，该注入面已在 `记忆系统提示词注入点分析.md:262-265` 记为 P1-2）：**加上 id 之后，模型第一次拿到可直接执行的句柄**，换行若不折叠，含换行的 content 可以伪装成另一条带 id 的记忆行。
- `recall.hideClosedTasks = true` 时 `done` / `dropped` 不进候选。**过滤点写死在 `hybrid-recall.ts` 闸门 1（`:158-161`）之后、项目加权截断（`:188`）之前**：自动注入 `topK` 只有 3（`config/thresholds.ts:25`），若照抄 `deleted` 的位置（`:195-196`，在截断与字符预算之后）再滤，3 条里滤掉 2 条就只剩 1 条、池中第 4-6 名永远补不上来，等于"随机丢注入"。开关开启时 `fetchK` 同 `sessionProject` 那样放大（`:151`），保证过滤后有足够候选；**过滤后不足 topK 不回退注入已关闭任务**（语义可预测；默认 false 时行为与现在逐字节一致）。

## 流程

### 主路径

1. **提取**：`l1_commit` 按上文位置校验顶层 `taskState`（缺省填 `open`），并回报 `taskStateIgnored` / `taskStateDroppedOnReplace` 软闸计数。
2. **agent 关闭**：agent 在注入块或 `recall_l1_records` 里看到 `[待办]` 的任务、确认已完成 → `l1_task_state({ids:[…], state:"done"})`；用户口头取消的 → `state:"dropped"`；重新开工 → `state:"open"`。
3. **用户关闭**：`/my-memory:l1:task` 先 `list` 拿到 id，再 `done` / `drop` / `reopen`。
4. **落盘**：写锁内定位每个 id 的最后一条活跃行 → 就地改写（`taskState` + `updatedAt` + 审计）→ 按分片原子 tmp+rename 回写。不动向量。
5. **可见**：下一次召回的注入行带新状态；`recall_l1_records` 返回体带 `taskState`；L2 增量投影带该字段。

### 意外与边界

| 场景 | 处理 |
|---|---|
| id 不存在 / 已被 `deleted` | 报错并列出该 id；其余 id 照常处理（部分成功如实回报，不用整批回滚——需在工具 description 里写明与 `l1_fix` 的单 id 全成/全败不同） |
| 重复标记同一状态 | 幂等无操作，回报 no-op 计数 |
| 写锁 10s 超时（并发提交中） | 返回失败并提示稍后重试，不降级为无锁写入（`write-lock.ts:29`） |
| 分片被 CLI 写者并发重写 | **已知缺口**：`l1-admin` 的 mjs 脚本从不取这把提交级写锁（`write-lock.ts:10-13` 自述"CLI 侧从未实现"）。新工具与 `l1_fix` 之间仍无互斥 ⇒ 批量标记/迁移应在无后台 L1 运行时执行，并在计划验收里留一条说明 |
| 给了非法 `taskState` 值 | `l1_commit` 硬闸拒绝整批；`l1_task_state` 直接拒绝该次调用 |
| `work_fact` 等类型带 `taskState` | 忽略该字段并计数（软闸），不拒绝批次 |
| 同一任务被 dedup 重写 | 靠"写入路径的字段继承"三条措施；继承失败时软闸计数可见 |
| L2 子代理看到已关闭任务 | 「相关任务与资产」只列 `open`；已关闭的不再列为待跟进 |
| 存量 `metadata.status` 与新字段并存 | 迁移只映射明确的 `done`（4 条），其余不猜；`metadata.status` 原样保留不删 |

## 风险 / 待确认

- **L2 侧对就地改动不可见**：`read_l1_increment` 按 `recordEpochMs(id) > cursorEpoch` 过滤（`l2/read-tool.ts:120`，`l2/config.ts:172-199` 同口径），旧 id 的就地改写永远不会进入增量 ⇒ 场景块里的任务清单会滞后到该场景下次被重写为止。这是**既有性质**（`l1-admin tombstone` 与 `l1_fix tombstone` 同样对 L2 不可见）。本计划选择接受并记录；后续可按需：(a) 继续接受；(b) 增量补水时对 `updatedAt > cursorEpoch` 的记录一并返回；(c) 状态变更时额外写一条轻量提示记录。
- **CLI 写者与新工具之间无互斥**：`l1-admin` 的 mjs 脚本从不取提交级写锁（`write-lock.ts:10-13` 自述的已知缺口），`lib.mjs:99-111` 的 `autoBackup → assertRunLockFree` 只查运行级锁。迁移与批量标记必须在无后台 L1 时执行。
- **`verify-tool-schemas.ts` 的第 5/6 节从未真正跑过**（`EXT_ROOT` 指向不存在的目录）：那两节的"无内联 required / 无 schema 告警"在别的机器上都是真空通过。修好 `EXT_ROOT` 是任务 3 的前置。
- **注入格式变更**：每行新增 id（约 +25 字符/条）、状态标签与换行折叠，会改变注入块的字节数；`verify-prompt-contracts.mjs:82,105-110` 用变量注入 `recordsLines`，只改 `index.ts` 拼装行不会破它，但 `shared#l1-selffix-hint` 的三处副本必须同步。
- **向量召回仍会命中已关闭任务**：这是有意设计（靠标签区分而非删除），若实际噪声明显，再考虑把 `hideClosedTasks` 默认置 true。
- **部分成功语义**：多 id 调用中个别 id 失败时报错但不回滚已成功的部分——与 `l1_fix` 的单 id 全成/全败不同，需在工具 description 里写明（用户预期待确认）。
- **`taskState` 常量必须零 import**：`l1_commit` 的 `execute` 在子代理进程里跑，`commit-tool.ts` 新增的静态 import 都会进子代理；故闭集常量按 `record-types.ts` / `project-scope.ts` 的先例放零 import 模块，落盘逻辑（fs + 写锁）单独一层。任务 1 与任务 3 因此不争同一个文件。
- **迁移范围**：`metadata.status === "done"` 的 4 条是可机械映射的全部；`decided` / `confirmed` / `deferred` 语义不明，一律留 `open`。
- **README 的工具/命令计数是历史实测快照**（写「18 工具 + 16 命令」）：当前工作区加载期实测 **18 工具 / 18 命令**（含未提交的 `config/model-setup.ts` 的 2 条命令；HEAD 为 16 条）；`/learn` 在 `session_start` 注册、`memory-reviewer` 的那条未挂载、`memory` 工具整块注释（`index.ts:1004-1071`）故不计。收口时按实测量，不要在新旧数字上做算术，并注明口径（含不含未提交改动）。
