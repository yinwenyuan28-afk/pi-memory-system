# detect 信号判定提示词（detector.ts 使用）

> 每个分节 = 一个 LLM 语义确认指令（信号词正则命中后调用）。
> 格式约定：`## 节名` 到下一个 `##` 之间为提示词内容。
> 修改此处即可微调判定行为，代码内置默认值兜底（md 缺失/损坏时用默认）。

## create

这条用户消息是否表达【产出意图】（要实现一个功能、产出文件/代码、设计产品/方案）？回答 JSON {"yes": true/false}

## accept

这条用户消息是否在【确认工作流完成/验收】（例如"可以了/完成了/就这样"）？注意：如果消息包含"还要/再改/还没/不行"则不是验收。回答 JSON {"yes": true/false}

## reject

这条用户消息是否在推翻当前工作流的方案/设计？如果是，属于哪种：
a) 完全放弃（"不做了/算了，不要这个了"）→ "abandon"
b) 推翻部分设计但需求仍在（"重来但还要做/换方式实现"）→ "evolve"
c) 不是推翻（只是普通否定/澄清）→ null
回答 JSON {"type": "abandon"|"evolve"|null}

## adjust

这条用户消息是否属于【对当前工作流的需求/方案/目标做调整】（仍在同一工作流语境，不是全新需求）？回答 JSON {"yes": true/false}

## child

这条用户消息提到的新需求，是【当前工作流的子任务/组成部分】，还是独立的新工作流？回答 JSON {"child": true/false}

## continue

这条用户消息是否在【延续当前工作流】（"接着做/继续/下一步"）？回答 JSON {"yes": true/false}

## implicitConfirm

之前的工作流疑似完成（所有任务已完成）。这条新消息是在【继续修改/补充当前工作流】还是【转入新话题/没有异议】（可确认工作流完成）？回答 JSON {"confirm": true/false}

## newRequest

这条用户消息是否在【开启一个与当前工作流无关的全新需求】？如果只是继续当前任务的讨论/指示/收尾（如提交、编译、检查），则不是。回答 JSON {"yes": true/false}
