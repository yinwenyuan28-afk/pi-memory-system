## 前置：加载记忆分类规则

先调 `load_memory_rules("always")` 来加载完整分类规则（scope 列表与边界）到上下文头部。之后所有 `memory` 调用都能准确选择 target。

## 任务

读取 `profiles/default/sub-memories/` 下所有 `.md` 文件，逐文件检查：

1. **重复检测**：是否存在两个文件内容高度重叠（如 git-commit-guide 和 gitee-setup 已合并为 git-guide）。重复则合并后删除旧文件。
2. **完整性检查**：每个子记忆是否在正确的 scope 目录下（scope 列表从记忆分类框架获取），文件名格式是否符合约定。不符合的移动到正确路径（需确认）。
3. **过时检查**：内容是否与当前代码或项目状态一致。明显过时的标记 `⚠ 可能过时` 到文件顶部。
4. **关联检查**：routes.md 中是否有对应规则？如果没有且需要，添加路由规则到 routes.md。
5. **精简检查（重点）**：单文件 >10KB（约 5000 中文字）视为臃肿，需精简为摘要卡片式——只保留**不可从代码/plan 重新发现**的内容（见下），完整细节留给 plan/ 和代码，在文件头部声明入口路径。

## 保存价值判断：不可重新发现的信息才值得存

整理/精简时用此标准判别一条信息去留：

**值得留的四个类别**（代码/plan 里看不出、丢了找不回）：

- 用户拍板的决策（"为什么这么设计"，如方案选型、推翻建议的理由）
- 踩坑经验（文档没有但验证过，反复踩成本高）
- 概念澄清（用户纠正过的认知，丢了回到错误理解）
- 未定事项（含已调研结论，防重复调研）

**不存的**：表结构字段明细、SQL DDL、接口清单、实现目录结构、审查修复逐条——这些可从代码/plan 重新发现，记忆里留副本必过时。

**大文档边界**：设计/架构文档全文不入记忆；记忆只留"决策摘要 + 入口路径"（如 `plan/xxx/YYY.md`）。

## 不处理

- 非 `.md` 文件
- `wangxin/` 目录（那是其他项目的记忆）
- `env/` 目录（开发环境配置）
