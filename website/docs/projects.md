# 项目归属与记忆空间

同时处理多个项目时，你希望 Pi 优先想起当前工作的约定，也能复用通用经验。扩展用项目归属和适用范围帮助排序；需要分开存储时，可以选择不同的 profile（记忆空间）。

## 项目、工作目录和场景

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| 工作目录 `cwd` | 会话从哪里启动？ | 从 `C:/work` 启动 Pi |
| 项目 `project` | 这条记忆关联哪个独立工作单元？ | 实际修改的是 `C:/work/order-service` |
| 场景 | 正在持续处理哪个议题？ | 订单服务的回调幂等性 |

项目是有专有身份、可以独立交付的最小工作单元。一个 Git 仓库可能包含多个项目；`src`、`backend` 等分类目录名称本身不足以确认项目。

会话从 A 目录启动后仍可能修改 B 项目，所以启动目录不能直接证明每条记忆的归属。

## 三种适用范围

| 范围 | 含义 | 示例 |
| --- | --- | --- |
| `self` | 只在某个具体项目成立 | 订单服务的回调幂等键约定 |
| `global` | 明确可以跨项目复用 | 一套通用排查方法或稳定协作偏好 |
| `unknown` | 证据不足，暂时无法判断 | 对话没有可核验的路径或有多个候选 |

`global` 与 `unknown` 的项目字段都留空。看到 `unknown`，表示系统没有可靠结论；它并不表示这条记录适用于所有项目。

## 系统怎样确定归属

后台提取可以为每条记忆附上来源消息和正文中出现的绝对路径证据。提交时核验路径是否确实出现在对应会话的来源正文中、是否位于候选项目目录下。显式证据不成立时，不用会话启动目录猜一个项目；项目专属记录可能降为 `unknown`。

没有逐条候选和证据的旧调用，可以沿用有效的会话项目判定。当前没有完整的运行时项目登记表，因此标签仍可能缺失或判错；正文路径核验也不能独自证明哪个目录才是最小可交付单元。

在对话中明确说出项目名称、路径和事实适用范围，有助于提供证据。保存后可在查看器核对标签。

## 项目如何影响召回

当当前会话有有效项目判定时，自动召回先找相似记录，再调整候选排序：同项目保持原分，其他项目的 `self` 记录相似度乘以 **0.75**；`global`、`unknown` 和缺少范围标签的记录不降权。

没有有效会话项目判定时，全部按原始相似度排序。主代理主动使用 `recall_l1_records` 查询时，当前也保持原始相似度顺序。

::: warning 多项目使用边界
跨项目记录仍可能被召回。项目标签用于相关性排序，不提供权限控制或严格过滤；不要依靠它隔离不同客户的机密资料。
:::

## 使用不同的记忆空间

每个 profile 有自己的记忆文件、模型配置、向量库和后台队列。需要分开积累个人工作与另一组工作时，可以切换空间。

在 **Pi 会话**中执行：

```text
/my-memory:profile list
/my-memory:profile switch client-a
```

第二条切换到 `client-a`；名称不存在时会创建空间。名称请使用简单的目录名。查看器默认读取同一份激活设置，切换后重新启动查看器以查看对应空间。

切换前已运行的任务仍按原空间收尾，原空间里的后续排队项在其有效会话恢复后继续派发。查看器也可以用显式 `--profile` 指定空间。

profile 把扩展数据分开存放，但共享宿主的技能目录仍可能被读取。它也不构成操作系统权限或模型服务的数据隔离；需要保密边界时还要检查宿主、模型服务与查看器的访问方式。
