# 快速开始

目标：装好扩展，跑通一次完整的"对话 → 归档 → 提取 → 查看"链路，并确认每一步是否真的发生。

## 环境要求

| 项 | 要求 | 说明 |
| --- | --- | --- |
| 系统 | Windows | 停止子代理依赖 Windows 进程树语义，项目归属判定按盘符路径规则 |
| Node.js | ≥ 22.13.0 | 扩展自身 `engines` 的下限 |
| Pi | 0.83.0 及以上 | 该版本要求 Node ≥ 22.19；两项同时满足时取较高者 |

这两个版本号来自不同来源，不要混用：22.13 是扩展能加载的下限，22.19 是 Pi 0.83.0 的要求。README 记录的实测组合是 Pi 0.84.2 / pi-coding-agent 0.83.0 / pi-ai 0.74.2，但这不是兼容版本清单。

## 1. 安装扩展

```bash
pi install npm:pi-memory-system
```

从本地目录安装（开发和验证改动时）：

```powershell
pi install ./path/to/pi-memory-system
```

然后在 **Pi 会话**里执行 `/reload`，或重启 Pi。

::: warning 只选一种安装方式
不要同时保留扩展扫描目录里的副本和 `pi install` 安装的副本，否则会重复加载、重复注册同名工具。`pi install` 不接受 `.tgz`，压缩包要先解包。
:::

后台子代理由扩展自己启动，不需要另外安装 pi-subagents。

## 2. 检查配置状态

```text
/my-memory:model:peek
```

它只读，不请求远端，显示四件事：

| 显示项 | 含义 |
| --- | --- |
| 后台 LLM | 后台整理用哪个模型；未指定时跟随前台模型 |
| Embedding | 是否配置了服务地址、密钥、模型与维度 |
| 向量化 | 开关状态、记录数、自动阈值 |
| 召回可用性 | 当前能否做语义召回 |

首次安装时向量化是关闭的。这不妨碍提取和保存，只影响"按问题含义检索"。

## 3. 做一次小规模验证

不要挑一次闲聊来验证。选一个你正在做的项目，说一条明确的事实或待办，比如：

> 这个项目的回调事件用事件编号做幂等键，另外要补一条重复投递的重试测试。

等回复结束，手动请求提取：

```text
/my-memory:l1-trigger
```

它会跳过 10 次输入的等待，但仍然进入同一队列。看到"已入队"只说明排队成功，不代表提取完成。

## 4. 确认结果

按顺序确认三件事，能更快定位是哪一步没发生：

| 检查 | 怎么看 | 期望 |
| --- | --- | --- |
| L0 是否归档 | `memoryDB/l0/conversations/` 有当天文件且变长 | 有你刚说的那几句正文 |
| L1 是否写入 | 查看器「L1 记录」页 | 出现新记录，类型与内容合理 |
| 向量是否建立 | `/my-memory:l1:embedding:list` | 记录出现在已向量化列表（需先开向量化） |

如果第一步就没有，问题在归档；如果归档有、记录没有，问题在提取或提交；如果记录有、召回不到，问题在向量或阈值。

## 5. 决定是否开启语义召回

想按问题的含义找回相关记录，需要配置 Embedding 服务并开启向量化：

```text
/my-memory:model
```

向导会让你选择后台模型、填写 Embedding 服务、决定是否开启向量化。几个容易混淆的点：

- **配置服务 ≠ 开启开关。** 填好地址密钥只是让服务可用，还需要显式开启 `vectorization.enabled`。
- **开启开关 ≠ 补齐历史向量。** 新提交的记录会向量化，已有记录需要用 `backfill` 补齐。
- **达到阈值 ≠ 手动不可用。** 自动向量化默认要最近 365 天满 500 条记录才触发，但手动补齐没有这个限制，少量记录也能建向量。
- **关闭开关 ≠ 清空向量。** 已有向量仍可用于召回，只是新记录不再自动写入。

修改 Embedding 配置后建议重启 Pi，让主进程与后台任务读到同一份配置。
