# 记忆如何工作

扩展把对话里的有效信息逐步整理成不同用途的记录。前台按当前问题召回 L1；场景与画像在另一条整理路径中积累。

## 用一个工作例子理解

假设你和 Pi 排查订单服务的重复回调，最终确认需要用事件编号做幂等校验，并留下“补充重试测试”的待办。

| 过程 | 可能留下的内容 | 下次有什么用 |
| --- | --- | --- |
| 归档对话 | 你们讨论问题、解释原因和确认方案的正文 | 保留提取依据 |
| 提取记忆 | “这个服务按事件编号去重”；“补充重试测试” | 回到相似问题时检索事实和待办 |
| 整理场景 | 回调排查的背景、适用条件、步骤与反例 | 把分散结论组织成可以阅读的工作经验 |
| 提出画像 | 多次工作中体现出的稳定协作偏好 | 审阅并入后帮助新会话理解你的工作方式 |

这是帮助理解的示例，实际保存什么取决于对话内容和模型判断。一次修复不一定足以形成长期画像。

## 四层各自负责什么

| 层 | 保存内容 | 如何参与工作 |
| --- | --- | --- |
| L0 对话归档 | 净化后的用户与助手正文 | 作为记忆提取的来源 |
| L1 原子记忆 | 事实、待办、方法、工作资产 | 供相关问题检索与召回 |
| L2 工作场景 | 有关联、有背景的记录 | 组织经历，供后续处理与画像生成 |
| L3 长期画像 | 用户特征与协作偏好提议 | 用户审阅并入后，作为新会话的背景 |

普通 L0 归档不包含工具调用和工具结果。技能学习有独立的 skill-feed，二者用途不同。

## 什么值得记住

开发模式把 L1 分成四类。每条应尽量能单独理解，不依赖“刚才那个问题”之类指代。

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| `work_fact` | 已确认的事实或约定 | 回调事件使用事件编号去重 |
| `work_task` | 需要跟踪的工作 | 为重试和重复投递补充测试 |
| `work_method` | 可迁移的判断原则、约束或方法 | 重试入口应先核对幂等边界，再判断是否可安全重放 |
| `work_artifact` | 可复用的工作产物或位置 | 已完成的迁移脚本用途及位置 |

后台提取会查询相似旧记录，决定新增、更新、合并或跳过。默认还会复核候选是否值得保存；复核失败时可能继续保存并留日志。因此记忆仍需要用户检查，提取质量也受模型影响。

主代理也可以在当前对话中直接保存 L1。你可以明确说“请记住这个项目的这条约定”，随后在查看器确认结果。主动保存不必等待自动计数，但不代表已经完成向量化或场景整理。

## 两条工作路径

**问题召回：** 对话 → L1 记录 → 建立向量 → 当前问题检索 → 相关记录参与回答。

**逐步整理：** L1 记录 → L2 场景 → L3 画像提议 → 用户审阅 → 正式画像。

场景层当前不会自动注入每轮回答。不要将“整理成场景”和“当前轮次带入全部场景”理解为同一件事。

```text
对话正文 → L0 归档 → L1 记录 ──→ 向量索引 → 相关问题的上下文
                       │
                       └──→ L2 场景 → L3 提议稿
                                         │
                                      用户审阅并入
                                         ↓
                                  新会话的正式画像快照
```

触发和完成的时间关系见[后台运行与故障恢复](./pipeline)。

## 场景怎样帮助理解经历

同一议题的多条记忆可以使用稳定场景编号归组。L1 的场景标签帮助提取时复用议题；L2 的场景文件进一步整理背景、适用条件、操作步骤、判断逻辑、反例、事实依据、相关任务与资产、演变和待确认问题。

场景标签、项目标签和 L2 文件名承担不同用途。一个项目可以有多个议题，一个议题可以经历多轮排查与实现。查看器可以展示场景内容及其成员记录。

活跃 L2 场景默认最多 15 个。暂时不用的场景可归档，保留内容、成员清单和归档理由，之后恢复；恢复需要空余名额。默认创建不足 7 个日历天的场景不能归档。归档场景不会删除其 L1 记录。

## 任务有自己的状态

待办可以是 `open`（待办）、`done`（已完成）或 `dropped`（已废弃）。完成一件事不等于删除它；“已经做过”也可能是有用的上下文。

通过本地查看器或 `/my-memory:l1:task` 管理状态。`recall.hideClosedTasks` 可控制是否在自动召回中排除已关闭任务。

## 质量分表示什么

查看器里的质量分结合有效命中、无效反馈和时间衰减。自动检索拿到候选还不算注入命中，相关记录真正进入回答上下文时才计数；主动工具召回在结果返回时计数。

新记录有 7 个日历天的保护期。通常的衰减按有会话归档的活跃日计算；没有归档数据时会退回日历时钟。这个时钟是整个记忆空间共用的，其他项目的活动也可能使旧项目的记录继续衰减。

低质量分可能只表示近期没用到。淘汰候选还要结合优先级、类型和使用反馈判断，不能看到“冷”就认为记录有错或应该删除。

## 画像由你确认

L3 将提议写入 `USER-temp.md`。它不会自动覆盖正式 `USER.md`。你可以在查看器检查、编辑并选择并入。

正式 `MEMORY.md` 和 `USER.md` 会在新会话开始时读取。并入画像后，要在后续新会话中使用更新的背景快照。

想了解这些资料如何控制对主任务的影响，阅读[上下文与渐进式设计](./context-design)：它解释注入位置、主会话历史边界、规则按需加载和后台上下文分离。
