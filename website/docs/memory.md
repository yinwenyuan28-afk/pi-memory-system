# 记忆如何工作

这页用使用视角讲：哪些内容会被记住、整理成什么、下次怎么用上。数据结构细节见[记忆模型](./memory-model)。

## 用一个工作例子理解

假设你和 Pi 排查订单服务的重复回调，最后确认用事件编号做幂等，并留下"补充重试测试"的待办。

| 阶段 | 留下什么 | 下次有什么用 |
| --- | --- | --- |
| 归档对话 | 你提问、解释原因、确认方案的正文 | 作为提取依据 |
| 提取记忆 | "回调按事件编号去重"（事实）；"补充重试测试"（待办） | 相似问题时被检索到 |
| 整理场景 | 回调查询的背景、适用条件、步骤、反例 | 把分散结论组织成完整经验 |
| 提出画像 | 反复出现的协作偏好 | 你确认后帮助新会话理解你的工作方式 |

这是帮助理解的示例。实际保存什么取决于对话内容和模型判断，一次修复不足以形成稳定画像。

## 四层各自保存什么

| 层 | 保存内容 | 参与方式 |
| --- | --- | --- |
| L0 对话归档 | 净化后的用户与助手正文 | L1 提取的输入 |
| L1 原子记忆 | 事实、待办、方法、工作产物 | 按相似度被召回；L2 的输入 |
| L2 工作场景 | 有关联、有背景的完整经历 | 供人阅读；L3 的输入 |
| L3 长期画像 | 用户特征与协作偏好提议 | 确认后作为新会话背景 |

普通 L0 归档**不含工具调用和工具结果**。原因和取舍见[记忆模型](./memory-model)与[数据说明](./data)。

## 什么内容值得记

`code` 模式把记忆分成四类。判据是"能不能脱离当前对话单独读懂"：

| 类型 | 判据 | 例子 |
| --- | --- | --- |
| `work_fact` | 已确认的事实或约定 | 回调事件用事件编号去重 |
| `work_task` | 需要跟踪的工作 | 补充重复投递的重试测试 |
| `work_method` | 可迁移的判断原则 | 重放前先核对幂等边界 |
| `work_artifact` | 可复用的产物或位置 | 迁移脚本路径与用途 |

反面例子同样重要。下面这些通常不该保存：

- 一次性的进度播报（"正在改第 3 个文件"）
- 没有根因的临时修复
- 能直接从代码或文档查到的事实
- 纯情绪表达

后台提取会查询相似旧记录，再决定新增、更新、合并还是跳过。默认还有一道价值复核：只判断"值不值得留"，不重写内容。复核失败时会放行并留日志，所以记忆质量仍需要抽查。

## 也可以直接保存

主代理在当前对话里发现值得记的内容，可以直接调 `l1_commit` 保存，不必等自动计数：

```text
请记住：这个项目的回调事件用事件编号做幂等键。
```

这条路径有三点不同：

| 方面 | 自动提取 | 主代理直接保存 |
| --- | --- | --- |
| 触发 | 累计 10 次输入 | 你明确要求 |
| 价值复核 | 会跑 | 不跑 |
| 处理进度 | 会推进 L1 游标 | 不推进，避免把未提取的对话标成已处理 |

直接保存不等于已经完成向量化和场景整理。向量要看开关与服务，场景要等下一次 L2。

## 两条工作路径

**问题召回**：对话 → 查到相关 L1 记录 → 插进本轮上下文 → 辅助回答。

**逐步整理**：L1 记录 → L2 场景 → L3 画像提议 → 你审阅 → 正式画像。

```text
对话正文 → L0 归档 → L1 记录 ──→ 向量索引 → 本轮上下文
                       │
                       └──→ L2 场景 → L3 提议稿
                                        │
                                     你确认并入
                                        ↓
                                 新会话的正式画像
```

## 场景怎样组织经历

同一议题的多条记录归入同一个稳定场景编号。议题不变时继续复用，议题改变时才新建。这条规则防止同一件事裂成十几个名字相近的场景。

场景正文固定九段：工作场景、适用条件、核心 SOP、判断逻辑、禁忌与反模式、关键事实依据、相关任务与资产、演化记录、待确认问题。九段是强制结构，写不全就说明这次整理还没想清楚。

活跃场景默认最多 15 个。暂时不用的可以归档：正文、成员清单和操作记录都保留，之后能恢复。归档不会删除其中的 L1 记录。

::: info 场景不进每轮回答
L2 场景目前**不会**自动注入到每轮回答。主代理拿到的只有 L1 记录。场景的用途是供 L3 归纳画像、供你阅读复核，以及作为未来的检索基础。
:::

## 任务有自己的状态

待办有三种状态：

| 状态 | 含义 | 可以做什么 |
| --- | --- | --- |
| `open` | 待办 | 完成或废弃 |
| `done` | 已完成 | 重新打开 |
| `dropped` | 已废弃，不再打算做 | 重新打开 |

完成一件事不等于删除它。"已经做过了"本身常常就是有用的答案，所以已关闭的任务默认仍会被召回，只是注入时带状态标签。

不希望看到它们时，把 `recall.hideClosedTasks` 设为 `true`。注意这会让检索量放大一倍：如果先取 3 条再过滤，滤掉 2 条就只剩 1 条，第 4 名永远补不上来。

## 质量分表示什么

查看器里的质量分结合有效命中、无效反馈和时间衰减：

```text
quality = 有效命中 × exp(-活跃日数 / 14) × 反馈惩罚
```

两个时间概念要分开：

- **活跃日**：有会话归档的日子。停工期间不增长，所以"很久没用到"和"很久没工作"能区分。
- **日历天**：真实经过的天数。只用于新记录保护（7 天）和"新"标签。

低分可能只表示近期没用到，不表示内容有错。淘汰资格另有一套判断：只有被反复召回又被判无效，或者长期闲置且内在价值低，才进入候选。高优先级、`work_method` 类、曾经有效使用过的记录受保护。

## 画像要你确认

L3 写的是 `USER-temp.md`，不是 `USER.md`。它不会自动覆盖正式画像。

你可以在查看器里检查、编辑、选择并入。默认并入策略是追加：保留正式画像现有条目，只补充提议稿里还没出现的条目。改写过的文本会被当成新条目，旧条目不会自动删除，所以看到新旧矛盾时需要人工整理。

正式 `MEMORY.md` 和 `USER.md` 在**新会话开始**时读取。并入之后要开新会话才会用到更新后的背景。
