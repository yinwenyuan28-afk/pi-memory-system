# 后台运行与故障恢复

记忆处理需要模型调用，通常不会在你发出一句话后立即完成。先区分四个阶段：累计输入、请求排队、子代理处理、提交成功。只有成功提交才代表该批输入已处理。

## 自动提取什么时候开始

L1 空闲时，每次来自交互界面的用户输入计数加一，默认累计 **10 次**。达到阈值后，等当前回复和代理活动结束，再检查归档并安排提取。工具调用和自动跟进不增加计数。

L1 已排队或运行时暂停计数，但对话仍进入归档。任务成功后还有未处理内容，会继续安排下一批，无需再等 10 次。每批最多读取 25 条新用户或助手消息；没有值得保存的候选时也可以提交进度，记录数不一定增长。

L1 积压排空且有新记忆时安排 L2。L3 会结合场景变化、首次生成、累计新记忆（阈值 30 条）和显式请求等条件评估画像更新。L1、L2、L3 共用串行队列，L3 排在后面。技能审查单独运行，使用自己的计数和进度。

```text
累计输入 → 请求排队 → 后台处理 → 成功提交 → 保存进度
                           │
                           └→ 失败或未提交 → 保留旧进度 → 后续触发再处理
```

## 怎样查看当前进度

Pi 底部状态栏显示 L1 距离触发的剩余输入次数、当前后台层和技能审查状态。剩余次数是触发计数，不是完成倒计时。

本地查看器的“流水线”页显示排队、运行和最近结束的作业，以及待消费的触发信号。查看器中的“请求入队”会先保存请求信号，需要有效 Pi 主会话在代理活动结束时消费；只开查看器不会独自执行提取。

| 看到的情况 | 表示什么 | 下一步 |
| --- | --- | --- |
| 已保存触发信号 | 等待 Pi 会话消费请求 | 回到 Pi，让一次当前活动正常结束 |
| 排队 | 请求已经登记，等待前面的作业 | 检查运行中的层 |
| 运行 | 子代理正在处理或等待模型 | 查看耗时与对应层日志 |
| 完成但没有新记录 | 可能没有值得保存的内容，或候选重复 | 查看结果、来源及价值校验留痕 |
| 连续失败后暂停 | 该层停止自动执行 | 修复原因后手动触发该层 |

## 手动请求处理

在 **Pi 会话**中执行对应命令：

```text
/my-memory:l1-trigger
/my-memory:l2-trigger
/my-memory:l3-trigger
```

按需要选择一层即可。手动触发仍进入同一队列；不会绕过正在运行的任务，也不保证画像立即生成。

## 失败后怎样恢复

未成功提交时保留旧处理进度，下次仍会读取未处理输入。部分数据已经写入的故障仍需检查结果，不能把保留进度理解成所有写入都自动回滚。

某层连续失败 **3 次**后暂停自动执行，其他未暂停层仍可继续。暂停状态会保存到磁盘，单纯重启不等于清除原因。

1. 在流水线页找到失败层和失败说明。
2. 检查后台模型是否可用、配额或网络是否异常；向量相关错误同时检查 Embedding 配置。
3. 修复后在 Pi 中手动触发该层；有暂停的排队项时会恢复原项。
4. 等成功提交，再确认记录、场景或提议稿及进度变化。

日志在当前 profile 的 `memoryDB/logs/`，可按 `l1`、`l2`、`l3`、`pipeline`、`recall` 等范围定位。共享错误信息前检查私人内容和配置密钥。

## 长时间运行与停止

当前内置软阈值是 **10 分 30 秒**（`630000` 毫秒），到点只记录日志并继续等待；硬上限是 **30 分钟**。实际值可由 `subagent` 配置覆盖。模型生成期间会话文件暂时没有增长，不能据此判断任务已经卡死。

需要提前停止时，优先使用流水线页的停止操作，或在 Pi 中运行：

```text
/my-memory:subagent-kill l1
```

将 `l1` 换成实际层。系统先阻止后台写入，给进行中的提交留出收尾时间，再停止并检查进程，确认退出后处理修复。不能确认停止时，会暂时隔离该层写入；不要自行删除锁文件来强制放行。

关闭主会话会停止新派发，已运行任务按原空间继续收尾。对应空间重新有有效会话后，已保存的后续作业才继续运行。
