# 整体设计

Pi Memory 是 Pi 编码代理的扩展。它做两件事：把对话里值得留存的内容整理成结构化记忆，并在后续回答前把相关记录交给模型。

这两件事走两条不同的路径，共用同一份记忆库：

<MemoryFlow kind="architecture" />

上图上半部分是**前台召回**，发生在本轮回答之前，只读。下半部分是**后台整理**，发生在每轮活动结束之后，只写。两条路径的交点是 L1 记录和它的向量索引。

## 两层职责

| 层 | 谁在跑 | 什么时候 | 读什么 | 写什么 |
| --- | --- | --- | --- | --- |
| 前台召回 | 主代理进程 | 每次模型调用前 | 向量索引、L1 记录、`MEMORY.md` / `USER.md` | 只读，不改变记忆 |
| 后台整理 | 独立子进程 | 每轮活动结束、计数达阈值或手动触发 | L0 归档、已有记录、已有场景 | L1 记录、场景块、画像提议稿 |

前台永远不写记忆，后台永远不参与当前回答。这个划分让"回答变慢"和"记忆写坏"互不影响：召回超时最多本轮没有记忆，后台失败最多这一批重做。

## 从一次对话看完整链路

假设你在排查一个订单服务的重复回调问题，最后确认了用事件编号做幂等。

1. 你发出问题。主代理启动前，扩展用你的问题构造查询，从向量库取出相关 L1 记录，插到消息里。
2. 模型回答，可能读代码、跑命令。这些工具调用和结果**不进入**普通对话归档。
3. 本轮活动结束。扩展把这一轮的用户与助手正文追加到 L0 归档，记录归档进度。
4. 累计到 10 次交互输入后，L1 任务入队。子代理读新增对话，提炼出"回调按事件编号去重"这类记录，通过提交工具写入。
5. L1 积压排空且有新记录时，L2 子代理把这些记录编进"订单回调幂等"这个场景块。
6. 场景变化和新记忆积累到阈值时，L3 生成画像提议，写入 `USER-temp.md`，等你确认。

第 5、6 步不是必然发生的，它们取决于内容、阈值和是否出错。

## 四层各自解决什么问题

| 层 | 解决什么 | 产物 | 谁读 |
| --- | --- | --- | --- |
| L0 | 把会话原始 JSONL 变成干净、可增量读取的对话正文 | 按天分片的 `conversations/*.jsonl` | L1 提取 |
| L1 | 把对话变成能单独引用的原子记忆 | `l1/records/*.jsonl`，可带向量 | 前台召回、L2 整理 |
| L2 | 把多条相关记忆编成有背景和步骤的完整经历 | `l2/scene-blocks/*.md` | L3、用户查看 |
| L3 | 从场景归纳长期协作偏好 | `USER-temp.md` 提议稿 | 用户审阅后写 `USER.md` |

分层的理由是各层的读取方式完全不同：L1 需要一条一条被检索，L2 需要整段被阅读，L3 需要整篇被注入。如果都塞进一张表，检索会变慢，阅读会变碎，注入会失控。

## 当前明确没有做的事

写清楚边界，比列出功能更能说明设计：

- **L2 场景不进前台自动注入。** 导航模块的开关默认关闭，且当前没有任何调用点；主代理每轮只拿 L1 记录。
- **项目标签只影响排序，不做硬过滤。** 跨项目记录仍可能被召回，只是被压低。它不是权限隔离。
- **L3 从不直接改 `USER.md`。** 只写提议稿，正式画像必须人工确认。
- **普通归档不含工具调用和结果。** 技能学习走独立的 skill-feed 通道，两套进度互不影响。
- **没有跨设备同步，也没有云端记忆。** 数据都在本地 profile 目录，需要备份就复制整个目录。

> 实现依据：[index.ts](https://github.com/yinwenyuan28-afk/pi-memory-system/blob/main/index.ts) 的扩展注册与会话事件处理；[memory/pipeline/worker.ts](https://github.com/yinwenyuan28-afk/pi-memory-system/blob/main/memory/pipeline/worker.ts) 的 `setupPipelineWorker()` 串行调度三层；[memory/l2/navigation.ts](https://github.com/yinwenyuan28-afk/pi-memory-system/blob/main/memory/l2/navigation.ts) 的 `L2_INJECTION_ENABLED = false`，全仓库没有调用 `buildL2Injection()` 的位置。

## 模块如何组合

| 需求 | 主要模块 |
| --- | --- |
| 扩展挂载、事件挂点、工具与命令注册 | `index.ts` |
| 会话归档与降噪 | `memory/l0/` |
| 原子记忆、场景池、质量与纠错 | `memory/l1/` |
| 场景块、成员清单、归档 | `memory/l2/` |
| 画像提议与条目编辑 | `memory/l3/` |
| 队列、失败暂停、停止、写者锁 | `memory/pipeline/` |
| 召回、向量库、Embedding | `memory/search/` |
| 命中统计 | `memory/stats/` |
| 提示词模板与渲染 | `prompts/`、`agents/` |
| 本地查看器 | `viewers/`、`scripts/l1-admin/` |

## 运行时还要关注什么

后台任务不只是"调模型"。它要回答四个工程问题：一批数据处理到哪儿了、失败了会怎样、同一个任务会不会被跑两次、慢到什么程度该停。
