# 沉淀可复用技能

有些经验适合存成事实，有些适合变成有输入、步骤和结束标准的操作指南。技能学习面向后者。

## 两类内容的分界

| 内容 | 例子 | 放哪里 |
| --- | --- | --- |
| 偏好、习惯、风格 | "讨论方案时先给结论" | L1 记忆或 L3 画像 |
| 一次性结论 | "这个版本的回调用事件编号去重" | L1 记忆 |
| 可重复执行的流程 | "排查支付回调的五步，含失败分支" | 技能 |

判断标准是**换一个类似问题还能不能照做**。能照做的写成技能，不能的写成事实。

## 主动发起

```text
/learn
```

也可以指定材料：

```text
/learn 请重点整理本次回调排查的方法
```

扩展还会周期性审查增量 skill-feed，默认累计 20 次交互输入后检查。

## 审查用什么输入

技能审查读的是 `skill/feed/`，与 L1 的 L0 归档是两条独立通道：

| 通道 | 保留哪些角色 | 用途 |
| --- | --- | --- |
| L0 归档 | 用户、助手正文 | L1 提取 |
| skill-feed | 用户、助手、工具调用、工具结果 | 技能审查 |

技能审查需要工具记录，因为"做了什么操作、拿到什么结果"是理解执行步骤的关键。普通 L0 归档不需要这些，原因见[数据说明](./data)。

两条通道各有自己的游标，互不影响。一次审查只用当前会话的 feed，不回溯所有历史会话。

::: warning skill-feed 可能含敏感内容
工具参数和结果会原样保留。命令里的路径、接口返回的 token、读到的配置文件内容都可能进入 feed，并在审查时发给配置的后台模型。默认清洗不保证识别凭据。
:::

## 生成后检查什么

审查会优先更新或补充已有同类技能，再考虑新建。生成后建议按顺序检查：

| 检查项 | 为什么 |
| --- | --- |
| 触发条件是否明确 | 太宽会到处触发，太窄永远不触发 |
| 输入是否写清 | 缺输入时执行会中断 |
| 步骤能否照做 | 抽象成"优化一下"就没法执行 |
| 失败分支是否覆盖 | 只写顺利路径的技能遇到问题就没用 |
| 验证标准是否可判 | "确认正常"不是标准 |

质量由提示词指导模型判断，仍可能出错。生成不等于正确，需要人工过一遍。

## 和记忆的边界

| 问题 | 答 |
| --- | --- |
| 技能会随会话注入吗 | 不会自动注入；由代理按需加载 |
| 技能存哪里 | profile 的技能目录，可被 `resources_discover` 发现 |
| 删除技能会影响记忆吗 | 不会，两者独立存储 |
| 一次对话能生成技能吗 | 能，但质量取决于这次过程是否完整 |

## 与 L1 审查的区别

早期版本还有一个独立的"记忆审查"子代理，负责复核 L1 记录质量。它已停用，质量判断现在分两处：

- **提交前**：`l1.valueCheck` 用一次模型调用判断候选值不值得留。
- **召回后**：命中统计与无效反馈影响质量分，进而影响淘汰判断。

技能审查仍在运行，但它只处理技能，不再复核记忆记录。看到旧文档提到"记忆审查子代理"时，那是历史机制。
